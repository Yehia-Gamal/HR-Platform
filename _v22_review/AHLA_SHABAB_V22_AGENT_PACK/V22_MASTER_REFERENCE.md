# 1A. قرارات الحسم والتحصين بعد المراجعة المستقلة

هذه القرارات ملزمة وتمنع عودة تناقضات V20.

## 1A.1 تصنيف النصوص التقنية

أي مثال SQL أو Dart أو TypeScript أو YAML داخل التوثيق يجب أن يحمل إحدى العلامات:

- `[قائم]`: موجود فعلًا وتم التحقق منه في المستودع.
- `[مقترح]`: تصميم مطلوب، لا ينسخ قبل مطابقته مع الـSchema والكود.
- `[توثيقي]`: مثال للشرح فقط.

ممنوع وصف كود بأنه قائم دون مسار ملف أو Migration أو Commit.

## 1A.2 حسم `USING(true)`

لا توجد قائمة ثابتة مسبقة من جداول `USING(true)`.

القاعدة:

- **Default Deny** لكل جدول.
- يسمح بـ`USING(true)` للقراءة فقط على جداول مرجعية عامة وثابتة بعد:
  - جرد الحقول.
  - التأكد من عدم وجود بيانات شخصية أو تنظيمية حساسة.
  - توثيق سبب السماح.
  - اختبار Anonymous/Authenticated.
  - اعتماد Security Reviewer.

ينشأ ملف:

`docs/security/RLS_PUBLIC_REFERENCE_ALLOWLIST.md`

ويحتوي لكل جدول:

- اسم الجدول.
- سبب اعتباره مرجعيًا عامًا.
- العمليات المسموحة.
- الحقول المستبعدة.
- الاختبارات.
- صاحب الاعتماد.

لا تعتمد أي قائمة قديمة متعارضة من V20. الجداول المرشحة مثل permissions/roles/shifts/holidays لا تُفتح تلقائيًا؛ يفحص كل جدول منفردًا.

## 1A.3 ترحيل RLS تدريجيًا

ممنوع استبدال `current_is_full_access()` في جميع السياسات دفعة واحدة.

المراحل:

1. إنشاء `has_scoped_permission()` واختبارها دون ربط.
2. إضافة السياسة الجديدة بجانب القديمة بصورة توافقية ومحدودة النطاق.
3. مقارنة القرارات في Shadow Logs.
4. تحويل Domain واحد فقط.
5. تشغيل RLS negative tests لكل دور.
6. مراقبة Staging.
7. إزالة المسار القديم بعد التحقق.
8. تكرار العملية Domain-by-Domain.

كل مرحلة لها Feature Flag وRollback Migration.

## 1A.4 مسار KPI المحسوم

المسار الوحيد:

```text
الموظف يرسل التقييم الذاتي
→ HR والمدير المباشر يعملان بالتوازي على حقول منفصلة
→ Barrier بعد اكتمال الاثنين
→ السكرتير التنفيذي يراجع من لوحة Admin
→ يرسل الحزمة للمدير التنفيذي
→ المدير التنفيذي يقر أو يطلب مراجعة
→ السكرتير التنفيذي يغلق الدورة
```

أي مسار تسلسلي قديم ملغى.

## 1A.5 الإجازة العارضة/الطارئة

القرار النهائي:

- تنفذ تلقائيًا دون موافقة إذا كانت السياسة `emergency_leave_auto_approval_enabled = true`.
- الشرط الافتراضي في Production يحدد بواسطة Main Admin بعد المراجعة القانونية.
- عند التفعيل:
  - رصيد كافٍ.
  - لا تداخل.
  - المدة والنطاق مستوفيان.
  - Audit وإشعار للمدير وHR.
- عند التعطيل:
  - تسلك مسار المدير المباشر.
- لا يوجد سلوك مزدوج غير موثق.

## 1A.6 لا جدول زمني ثابت

لا تعتمد أسابيع ثابتة مثل 6 أو 10 أو 16.

يعتمد التنفيذ على Gates:

- Discovery Gate.
- Security/Data Gate.
- Core Features Gate.
- Integration Gate.
- Release Gate.

أي مدة داخل مستند قديم تقديرية وغير ملزمة.

## 1A.7 الموظف متعدد الإدارات

لا يؤجل المطلب، لكن ينفذ على مرحلتين:

### المرحلة الأساسية P0

- Schema يدعم Primary Assignment وSecondary Assignments.
- الطلبات والحضور وKPI تعتمد Primary Assignment.
- الموظف لا يتكرر.

### المرحلة الموسعة P1

- تقارير توزيع الوقت.
- نسب التخصيص.
- المدير الوظيفي الثانوي.
- لوحات متعددة الإدارات.

هذا يمنع تعطيل الوظائف الأساسية.

# 1B. ضوابط Migrations والتوازي

## 1B.1 تسمية Migrations

استخدم Timestamp UTC كاملًا بدل أرقام قصيرة:

`YYYYMMDDHHMMSS_description.sql`

مثال:

`20260726143015_add_role_templates.sql`

## 1B.2 منع التصادم

إضافة فحص محلي وCI:

```bash
#!/usr/bin/env bash
set -euo pipefail

duplicates="$(
  find supabase/migrations -maxdepth 1 -type f -printf '%f\n' \
  | cut -d_ -f1 \
  | sort \
  | uniq -d
)"

if [ -n "$duplicates" ]; then
  echo "Duplicate migration timestamps:"
  echo "$duplicates"
  exit 1
fi
```

ويفشل CI عند:

- Timestamp مكرر.
- ترتيب زمني غير صالح.
- تعديل Migration منشورة.
- Migration بلا Rollback/verification notes.

## 1B.3 Squash

لا تعمل Squash على Production history.

يسمح بإنشاء Baseline جديدة لبيئة تطوير جديدة فقط بعد:

- نقطة إصدار مستقرة.
- Backup.
- Schema diff = صفر.
- موافقة DBA.
- الاحتفاظ بالتاريخ الأصلي للأرشيف.

# 1C. الحضور والورديات والأداء

## 1C.1 Geofence قابل للضبط

- القيمة الافتراضية: 300 متر.
- التخزين لكل Work Site.
- الحقول:
  - `attendance_radius_meters`
  - `max_location_age_seconds`
  - `max_accuracy_meters`
- تعديلها من Main Admin/HR بصلاحية منفصلة.
- حدود آمنة تمنع قيمة صفر أو نطاقًا مبالغًا فيه.
- كل تعديل Audit ويطبق على الطلبات الجديدة فقط.

## 1C.2 الورديات الليلية

ممنوع إغلاق اليوم عند 23:59 بصورة عامة.

الإنهاء يعتمد على:

- `work_date`
- `shift_start`
- `shift_end`
- `crosses_midnight`
- `grace_period`
- المنطقة الزمنية `Africa/Cairo`

تغلق الوردية بعد:

`shift_end_datetime + checkout_grace`

مع Idempotency Key للموظف والوردية.

## 1C.3 مراقبة فشل التسوية

Job التسوية:

- Retry تلقائي.
- Dead-letter/Audit عند الفشل.
- Alert إذا لم تنتهِ وردية مستحقة خلال نافذة محددة.
- Dashboard لحالة آخر تشغيل.
- Backfill يدوي آمن بمدى تاريخ.

`detect_and_raise_alerts()` أو البديل القائم يتحقق من:

- آخر نجاح.
- عدد الورديات غير المسواة.
- مدة التأخير.
- الخطأ الأخير.

## 1C.4 محاولة حضور بلا اتصال

لا تعتبر حضورًا.

يمكن تخزين سجل محلي محدود:

- وقت المحاولة.
- سبب الفشل.
- حالة الشبكة.
- دون نجاح أخضر.
- دون تعديل الحضور.

بعد تكرار الفشل:

- إشعار للموظف.
- خيار طلب تصحيح.
- تنبيه HR وفق threshold.
- لا إعادة إرسال Challenge منتهٍ كحضور.

## 1C.5 `captured_at`

وقت العميل ليس مصدر الحقيقة.

- `server_received_at` هو الوقت المعتمد.
- `captured_at` دليل مساعد فقط.
- يرفض إذا كان قديمًا أو في المستقبل خارج tolerance.
- لا يسمح بتسجيل Offline Punch بالاعتماد عليه.

# 1D. اختبارات الحمل وحدود المنصة

## 1D.1 Baseline

قبل التحسين، قِس:

- عدد الموظفين النشطين.
- ذروة الحضور المتوقعة في الدقيقة.
- عدد RPCs.
- زمن الاستجابة.
- DB CPU/Connections.
- Edge Function latency.
- FCM dispatch rate.

## 1D.2 Load Profiles

اختبر على Staging:

- الذروة المتوقعة.
- 2× الذروة.
- 3× الذروة لمدة قصيرة.
- حضور متزامن.
- فتح كشف الشهر.
- إرسال منشور للجميع.
- طلبات موقع متزامنة ضمن الاستخدام المشروع.
- RLS query performance.

معايير القبول تحدد بعد Baseline، لكن يجب ألا يحدث:

- Duplicate punch.
- تجاوز اتصال قاعدة البيانات.
- Deadlock.
- فقد Notification Event.
- خطأ صلاحيات.
- انهيار واجهة.

## 1D.3 Connection Pooling

- جرد Supabase plan limits.
- استخدام Pooler للعمليات المناسبة.
- عدم فتح Connection لكل عنصر.
- ضبط timeouts.
- مراقبة saturation.
- Pagination وIndexes.
- توثيق حد الاستخدام المتوقع وخطة الترقية.

# 1F. إدارة الجهاز وتغييره

قاعدة جهاز نشط واحد تبقى، مع Recovery Flow:

1. المستخدم يطلب تسجيل جهاز جديد.
2. الجهاز القديم يظل نشطًا حتى:
   - اعتماد HR/Main Admin.
   - أو سحب يدوي موثق.
3. بعد الاعتماد:
   - الجديد نشط.
   - القديم ملغى.
4. عند فقد الهاتف:
   - HR يسحب الجهاز القديم.
   - يسحب الجلسات.
   - يطلب إعادة توثيق.
5. لا يوجد Lockout دائم بسبب هاتف مكسور.
6. إشعار أمني عند التغيير.

- مركز الطلبات.
- Organization Chart.
- أي تغيير عالي الخطورة.

لا تستخدم Flags لتجاوز RLS؛ هي للتحكم في العرض والتدفق فقط.

| مدير الموارد البشرية | `hr-manager` |

لا تنشأ حسابات مكررة للأدوار. المستخدم يمتلك:

- Role Template أساسي.
- Capabilities إضافية.
- Assignments تنظيمية.

# 2. الأدوار المعتمدة

## 2.1 السكرتير التنفيذي — Main Admin

- أعلى صلاحية إدارية.
- يعمل من لوحة الويب.
- يفتح:
  - مساحة الإدارة الرئيسية.
  - مساحة الموارد البشرية.
- يدير:
  - الأدوار والصلاحيات.
  - الموظفين.
  - دورة KPI.
  - الطلبات والتصعيدات.
  - لجنة المشكلات.
  - التقارير.
  - الإعدادات.
- لا تظهر صلاحيات الإدارة الكاملة في هاتفه.
- كل إجراء حساس يسجل في Audit Log.

## 2.2 مدير الموارد البشرية

- يفتح مساحة HR فقط.
- لا يفتح `/admin/*`.
- يدير:
  - الموظفين.
  - الحضور.
  - التصحيحات.
  - الإجازات الرسمية.
  - أرصدة الإجازات.
  - درجات HR في KPI.
  - تنفيذ الجزاءات المعتمدة.
  - اعتماد أجهزة الموظفين.
  - منشورات HR.
- لا يستطيع:
  - إنشاء Admin.
  - إنشاء Executive.
  - إنشاء Executive Secretary.
  - منح Full Access.
  - فتح/غلق دورة KPI.
  - طلب موقع الموظفين.
  - تعديل درجات المدير.

## 2.3 المدير التنفيذي

- لا يخضع للحضور أو KPI.
- يرى جميع التقارير والملخصات.
- يطلب الموقع المباشر.
- يستقبل مواقع الموظفين.
- ينشر قرارات وتنبيهات وتصويتات.
- يرى القضايا المصعدة.
- يوافق أو يرفض الجزاء الإداري.
- يعتمد طلبات Operations الشخصية.
- يطّلع على التقييمات النهائية بعد مراجعة السكرتير التنفيذي.

## 2.4 مدير التشغيل Operations

- يرث صلاحيات الموظف والمدير في نطاقه.
- يدير المأموريات والقوافل والفاندي.
- يقرر بالإنابة فقط عندما:
  - يكون المدير المباشر للموظف هو المدير التنفيذي.
  - تنتهي المهلة، افتراضيًا 6 ساعات.
  - يكون مخولًا فعليًا.
- يسجل القرار باسم منفذه الحقيقي.
- لا يعتمد طلبه الشخصي.
- لا يعدل رصيد الإجازات.

## 2.5 عضو لجنة حل المشكلات

- Capability إضافية بجانب الدور الأساسي.
- يرى القضايا المسندة للجنة.
- يسجل الرأي والإجراء المقترح.
- لا ينفذ الجزاء.
- لا يتخذ القرار النهائي.
- العضوية تدار من Main Admin.

## 2.6 المدير المباشر

- كل صلاحيات الموظف لنفسه.
- يرى مرؤوسيه فقط.
- يقبل/يرفض/يعيد طلباتهم.
- ينشئ تكليفات لفريقه.
- يراجع بنوده في KPI.
- لا يعتمد طلبه الشخصي.
- لا يعدل درجات HR.

## 2.7 الموظف

- حضور وانصراف.
- إجازات وأذونات.
- مأموريات وقوافل وفاندي.
- تصحيح حضور.
- تقييم ذاتي.
- قضاياه.
- منشورات وإشعارات.
- حسابه وجهازه.

# 30. الأمر النهائي للوكيل

نفّذ هذه الخطة داخل النظام الحالي فقط.

- لا تنشئ مشروعًا موازيًا.
- لا تعيد صفحات ملغاة.
- لا تستخدم Workflow قديمًا.
- لا تعرض Permission خامًا.
- لا تنشئ بيانات وهمية.
- لا تحذف البيانات التاريخية.
- لا تغلق أي بند دون Runtime Evidence.
- أي اختلاف بين الكود وهذه الخطة يحل لصالح هذه الخطة ما لم يسبب فقد بيانات.
- عند خطر فقد البيانات، سجل Blocker واستمر في المهام المستقلة.
